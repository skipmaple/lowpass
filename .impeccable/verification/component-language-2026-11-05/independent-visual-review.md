# Lowpass A / B / C 真实组件差异化复核

独立只读设计评估，供主任务综合与用户审核；这不是修改方案已获批准，也不是单独宣称完成整套 Impeccable critique。按父任务的具体 brief 判断，无新增访谈。2026-11-05。

## 结论

用户对“输入框与按钮全是 radius 0，看起来像同一套”的判断成立，但问题比圆角更深：**三套主题的刊头、文字与阅读构图已经分开，控件仍大面积继承旧纸刊的同一套“透明矩形＋墨色细线＋反白选中＋外描双框＋墨从底部漫满”语法。** 从刊头进入搜索、来源表单或确认框后，三种气质骤然收敛。圆角是最显眼的症状，单改 radius 仍会留下同样的层次、状态与交互感觉。

不建议为差异而让每个属性都不同。语义、顺序、44px 目标、键盘、radio/select 原生能力、删除确认、收藏/撤销位置应共享；有理由的区别落在轮廓、表面、选中方式、焦点与展开层次上。保留 A 的彩色色面边界、B 的中轴/序号方框、C 的深色阅读结构。不要把正文与刊头都磨圆，也不要给 C 每个控件切角。

## 已确认的核心事实

1. 来源表单 `.field-input` 三主题计算样式均为 `border-radius: 0px`、透明底、44px 高；focus 都是 2px `--ink` 外描边、2px offset。C 的 `--ink` 为 `#ECEDE7`，因而普通边框与 focus 接近白色。登录框虽提高到 48px 和更淡边色，形态与双框焦点仍一致。
2. `.seg-item`、`.btn-primary`、`.ctrl`、`.chip-outline`、日期输入、收藏来源 select 没有一套主题各自的控件形态；同样的选择方法以 ink 填满，在 C 就成为白块。背景和字型改变了，语法未改变。
3. 菜单的同纸底＋1px 边框、外观选项的 radio＋字母色块＋说明、dialog 的 480px 方框＋2px 顶线＋相同按钮排布均共享；C 对话框还使用与页面相同的最暗 `--paper`，在暗遮罩上主要靠白边辨识。
4. 已存在真正的构图差异，不能抹掉：A 的彩色刊头/模块面，B 的精确刊头、文字对读与贯穿中轴，C 的暗阅读平面、边缘索引。手机继承它们后，控件区仍明显同构。
5. 直角并非在所有处都错。B 序号框压轴和连线、A 满出血刊头色面、C 阅读平面折角都属于结构。输入与按钮属于操作，两者不必共用同一个 shape 规则。

## 一条应优先修的真实状态缺陷

**[P1] 外观菜单与账户菜单可同时打开，外观面板遮住账户菜单。**

实际步骤：`/settings` → 打开外观 → 点击页面标题，外观仍 open → 点击“账户”，账户 `aria-expanded=true`，外观仍 open。三主题均复现。A截图可见账户的关闭图标与右侧边框，却几乎看不到菜单内容，用户会以为账户打不开。

- 证据：`/tmp/lowpass-component-review/daybreak-1440-both-menus.png`（B/C同名文件亦有）；`overlay-behavior.json`。
- 当前外观是 `<details>`，只处理自身 Escape；账户是受控 menu，有 click-away 和 Escape。功能相邻却没有共享的“当前打开哪个浮层”规则。
- 建议：两个面板互斥；点外关闭、Escape关闭、关闭后焦点回到触发器规则一致。切换主题时保留表单/阅读位置是既有要求；关闭行为不是必须为三主题制造差异的领域。
- 没有证据支持“所有dialog焦点不可见”：真实Tab后取消按钮在A/C是主题accent 2px外环、B为黑色2px。保留它们的可见性，改的是与控件轮廓/填充的关系。

## 三套应该保留与补齐的边界

### A

应是**温润的工具面嵌在明亮刊物里**。强色面和锐利切分留给刊头、来源连续带；手会触碰的字段/按钮适度软化，日常反馈靠柔和的面、轮廓与稳定留白。不做所有按钮胶囊、不做每篇文章一张圆卡、不把金色用作正文。

### B

应是**有编辑秩序的精确工具**。中轴、序号框、表格规则和刊头继续保持锐利；输入/按钮可微圆，让“资料结构”和“可操作物”区分开。不是把表单也变成一张报纸；不需要为了不同而另造奇怪checkbox或日期控件。

### C

应是**暗面中有舒适层次的阅读与操作**。用三档surface和清楚的亮度关系取代“每个边框都接近白色”；金色集中标识当前位置/焦点/少量主要动作。操作控件可以小圆角，折角只属于既有阅读平面。不能变成全金、切角科幻、霓虹光晕或一堆高亮白按钮。

## 建议审核与验收顺序

1. 先批准三个主题的控件语法（上面的表面/形状/层级方向），不先拍板一张全站radius表。
2. 以真实组件建立一个可对照状态集合：登录/来源字段、主次按钮、搜索筛选、主题选项、菜单、dialog、就地反馈；A/B/C同时展示 default / hover / keyboard focus / selected / disabled / error / pending。未获批准前不改实现。
3. 先修外观/账户互斥，再让 shared components 读取语义tokens；检查旧 `tokens.css`、`motion.css` 的遗留默认与 `themes*.css` 的覆盖关系，避免“新底色被旧伪元素盖住”。
4. 验收应覆盖真实登录、搜索、收藏、账户、后台来源/设置，1440与390，并抽320；保留B中轴与刊头已确认内缩、A色面边界、C阅读层。检查不同输入类型、长中文、禁用、错误、键盘和reduced motion。不要只出一张默认组件拼图后宣称完成。
5. 修改审核通过后再同步 `DESIGN.md` 的 Shapes/Components。它目前“以直角为主”是对现状的描述，不该被用来否决用户这次针对统一直角的明确反馈。

## 本轮评价的实用边界

- 产品特异性：阅读大结构强；控件层中等偏弱，尤其来源表单与overlay可被其他产品直接复用而不损失身份。
- 可继续保留的优点：主题字体选择明确；真实内容/来源组织保留；44px与原生radio/select/可见焦点基本框架合理；B精确中轴及C暗阅读理念值得继续。
- 主要风险：把“差异化”机械理解为所有属性三分；把“温润”做成全圆卡；把C暗主题做成低对比；用大动效掩饰控件结构缺失。
- 用户情绪路径：刊头给出鲜明期待，进入表单后个性减弱；C表单白框/白块密集时显得像系统设置而非舒适阅读工具；打开两个菜单的重叠直接打断信任。
- Questions skipped: 本子任务是父任务已给定的只读审核 brief；由父任务向用户呈现可审阅方向，不重复向用户发问。
