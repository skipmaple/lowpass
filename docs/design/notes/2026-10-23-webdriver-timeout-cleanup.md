# 等待超时后仍保留可读的浏览器诊断

PR #75 首轮远端系统测试在既有滚动恢复条件处五秒超时，随后截图读取到了数字、数组，窗口重置也报错。原始日志保留；同提交重跑通过并不证明首次滚动超时原因已经解决。

## 已证明的连接问题

固定项目的 Ruby 3.4.8、selenium-webdriver 4.50.0、timeout 0.6.1、net-http 0.9.1 后，loopback WebDriver fixture 复现了这一机制：默认 `Timeout.timeout` 通过内部退出异常打断 HTTP read，Net::HTTP 的标准异常清理未关闭连接。下一条截图可能读到上一条 execute 的数字结果，后续命令继续错位。

显式传入 `Timeout::Error` 后，execute POST 的错误路径关闭旧连接，截图自动重新连接并收到自己的结果。这里保留现有五秒参数、0.1 秒轮询、页面条件和全部断言。未将超时改成通过，也未延长等待。Net::HTTP 对幂等请求另有重试逻辑，因此不将结论外推为任意谓词的精确物理五秒截止保证。

## 回归与反例

新增测试直接调用实际 `ApplicationSystemTestCase#wait_until`，使用真实 Selenium HTTP 客户端和随机 loopback 端口。夹具先返回不满足条件的数字，让轮询保持连接活跃；从首条 execute 起第四秒保留下一条响应，直到 helper 超时后才释放。随后检查 base64 截图、窗口列表、解码 PNG，以及后续三条命令使用第二条连接。

该测试放在 `test/system/`，本条协议回归不启动浏览器、HTTP 仅访问 loopback。系统测试基类的 `driven_by` 加载时会触发 Selenium 驱动发现，冷缓存时可能下载驱动，因此不从普通 Rails 单元测试引入这一依赖；完整系统套件本身仍使用真实 Chrome。

最初把第一条请求直接阻塞五秒的夹具在旧实现上也通过了：默认两秒 keep-alive 到期会在下一条命令前重连，掩盖问题。因此保留这份实验日志，采用持续轮询后再阻塞的回归，不改变实际 helper 参数。修订回归在旧实现明确失败：预期 PNG base64，实际为 `137`（1 failure / 0 errors）；修正后 1 项 / 7 assertions 通过。

独立审查后调整夹具计时起点及测试所在套件，最终完整本地 `bin/ci` 退出 0（61.92 秒）：454 项前端、856 项 Rails / 3763 assertions、78 项系统 / 8051 assertions。首屏 264.56 KB / 300 KB；现有两项 npm moderate 告警保留，high 门禁通过。测试使用项目测试库 fixture / seed。

## 首次滚动超时仍未确定

对原 PR #75、原随机种子 40713 的一次四 worker 全量系统诊断运行通过（77 项 / 8044 assertions）。钩子只记录原有 WebDriver 命令返回值，没有额外查询浏览器，也未改等待与断言。目标位置为 1255px，首次返回在第一次检查时已恢复；第二次返回先读到 0，下一轮读到 1255。该样本不解释原远端失败。

静态审查保留一个未验证的 Inertia 滚动 debounce / 当前 history 快照写入时序假设，未据此修改产品代码。本补丁仅防止已证明的 execute 响应错位，以便真实超时仍明确失败、后续诊断能继续读取。未部署、未修改已发布内容、未调用模型或写真实业务数据；获奖品质目标和完整历史恢复验收仍未完成。
