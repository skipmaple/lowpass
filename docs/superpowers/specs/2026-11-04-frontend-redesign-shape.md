## 1. 任务与用户

站长与受邀技术读者在手机、电脑上阅读同一份技术刊物。用户明确不喜欢当前前端，认为此前重构后层级与细节混乱；本次目标是重新设计整个前端，达到 fancy、流畅、令人愉悦、有设计感的整体体验。

读者页面以 Read 为主；搜索、收藏、账户和后台以 Operate 为主。阅读页的表现力来自编排与细节，后台的表现力来自秩序、密度和反馈，二者共用一种视觉语言，但不强行使用同一版式。

## 2. 结果与证据

主要路径是打开当期 → 连续浏览各源 → 阅读原文或收藏 → 离开后能找回。另一条是发现运行异常 → 找到具体源/期 → 了解影响与操作成本 → 发起处理 → 看见真实结果。

设计验收应能直接回答：现在是哪一期、哪个来源；条目原文、译文、推荐理由分别是什么；下一步可做什么；操作是否成功。不能靠增加口号、重复说明或缩小文字制造清晰感。

## 5. 内容范围与状态

- 日刊通常每源最多 10 条，但数量可配置；允许 0 条、单源缺失、长源名以及只有原文、没有译文/理由的条目。
- 标题上限 300 字符、摘要/译文简介 500 字符、周刊正文 50000 字符；长 GitHub 仓库名、CJK/Latin 混排、数字与 URL 都要有可读的断行规则。
- 日刊保留完整原文/已存摘要；搜索/收藏使用既有片段规则。不得为排版擅自删除内容，推荐理由缺失不得出现空装饰。
- 生成中、空刊、缺期、单源失败、不可回填、修订；搜索初始/加载/空结果/限流/不可用/无效查询；收藏请求中/失败/已取消/可恢复；表单校验/草稿未保存/提交中/成功/失败，均有明确结构。
- 后台理由与译文任务的预览范围、预算、真实请求结果及禁止重复提交属于任务信息，不因精简文案而隐藏。

## 6. 交互与布局意图

### 信息架构

建议把日刊、周刊、搜索、收藏作为读者的稳定入口；账户菜单保留身份和账户操作，管理入口只给管理员。收藏从仅头像菜单提升为常用入口属于本次建议，随整份简报确认，尚未修改 D29。

阅读采用连续单列正文，桌面可以用侧边留白安置来源/板块导航；侧栏不得挤压正文。手机导航改成紧凑入口或原生展开，不把桌面侧栏缩小塞进去。日期与前后期操作同组；下一期不可用时清晰禁用。

### 内容层级

每条由「标题与对应译文」「摘要/正文」「推荐理由与兴趣领域」「元数据与收藏」形成稳定关系，实际不存在的区域自然省略。原标题与原文链接继续保留，GitHub 仓库名不译。字体选择以完整文本角色为单位，不再把每个混排字符拆成风格零件。标题、中文译文与正文的大小和对比共同决定优先级，不靠每段增加边框。

推荐理由是刊物附加判断，必须与源站摘要和中文译文可区分；不新增逐条 AI 核验徽章、空标签、成功率或未经验证的说明。

### 流畅与愉悦

动效只用于表达位置与状态：页内目录定位、换期过渡、收藏反馈、菜单与对话框展开。响应即刻可见，持续时长建议控制在约 150–240ms，再按选定方向校准；正文默认可见，浏览不等待入场动画，不接管自然滚动。

来源切换通过稳定的栏目开篇与当前目录状态表达；不把来源标题、分隔与首条拆成互相追赶的动画。收藏在原位明确响应，错误恢复真实状态；异步操作反馈保留在发起处。浏览器返回恢复查询/滚动/焦点，保持深链与键盘能力。

### 响应式与无障碍

同时评审 390px 和 1440px 的代表页面，再检查 320/375、768/1024、1920px 及文本放大。窄屏长标题不横溢，关键操作保持至少 44px 触控目标。表格在小屏按记录分组，不隐藏身份、状态、时间、风险与操作。弹层保证焦点管理、关闭、焦点返回和不被容器裁切；无障碍名称与视觉状态一致。

阅读行长控制在约 60–75 个拉丁字符的量级，中文按实际字面调整。正文/译文建议从 16px 起评审，不能用灰度过低的小字充当精致。正常文本对比度至少 4.5:1；状态同时有文字或图形含义。遵从 reduced motion；打印包含所有来源并隐藏交互件，保留不可拆开的标题/内容组。
